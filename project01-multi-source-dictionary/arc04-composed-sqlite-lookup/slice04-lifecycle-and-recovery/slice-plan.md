## Binding catalogue2 and migration contract

1. New roots initialize schema2. New binary reads compatible schema1 and2, but every schema1 mutation except explicit migrate returns typed MigrationRequired; reads never auto-migrate. Existing signatures stay available, with this documented write prerequisite. All new writers recheck schema2/fence after acquiring BEGIN IMMEDIATE, not only before lock.
2. Schema2 stores explicit nullable active-generation identity (catalogue meta empty string encodes none; public generation remains Option). Reads/current_members/inspection/owned paths/install/query use that pointer. Null means no active aggregate and NEVER falls back to newest historical row. Historical generations, registrations/descriptors and input locations remain immutable/retained.
3. To fence an old binary that opened a writable connection before migration, transactionally rename each of the six old tables to its fixed `<name>_v2` physical name. Keep ONLY catalogue_meta as a read-only compatibility view exposing exact key,value columns from catalogue_meta_v2, no INSTEAD OF triggers. All other original table names are ABSENT after migration. New v2 reads/writes use physical names; new binary v1 readers use the six original physical names via a fixed version-to-SQL mapping. Never accept caller-provided SQL identifiers. Old fresh opens see meta schema_version2 and reject; a preopened old writer cannot read registrations/current_members to return a false idempotent success. Its original non-meta SELECT and every old-name mutation fail before activation; the meta view rejects writes. Merely blocking writes while exposing misleading historical members is insufficient.
4. Explicit `migrate(ROOT, expected_revision)` supports only exact schema1→2 or an idempotent already2 observation at the expected revision. Check expected revision under the transaction, checked numeric increments, original family/host/path encoding, known six-table layout and no conflicting destination objects. Validate registrations/member JSON and exact installed_heads versus latest-generation members, identity/kind/known-registration consistency; registered-only requires no heads and no active generation. Reject inconsistent metadata rather than guess a head. Do not read/hash complete payloads or call this a dictionary audit.
5. Rename all tables before creating the single meta view; inspect actual SQLite FK rename results and foreign_key_check under the same transaction. Expected FK targets are registrations_v2 and generations_v2. Do not change foreign_keys/legacy_alter_table opportunistically. Set version2, active pointer and revision+1 in the same successful commit. No public schema1 write window after commit. A failure or Busy at COMMIT must explicitly rollback and preserve schema1/prior activation, or truthfully report indeterminate with both concrete causes.
6. DELETE-journal pinned old readers can block migration commit. Test Busy+confirmed rollback/prior1, drop reader then successful retry; do not promise migration succeeds while that reader holds its transaction. A modeled preopened old writable connection without read transaction is a different case: migrate, then exact old reads/no-op paths and writes reject via absent old names or the read-only meta view. Captured v1 binary postmigration rejection is actual binary proof; modeled old SQL is not mislabeled a paused-binary race.

## Initial public API / CLI and execution flow

- `CollectionCatalogue::schema_version(&self) -> Result<u32, CollectionError>`.
- `CollectionCatalogue::migrate(root: impl AsRef<Path>, expected_local_revision: u64) -> Result<CollectionCatalogueMigrationReport, CollectionError>`.
- `CollectionCatalogue::update(root: impl AsRef<Path>, request: CollectionRequest<'_>, expected_local_revision: u64) -> Result<CollectionMutationReport, CollectionError>`.
- `CollectionCatalogue::rebuild(root: impl AsRef<Path>, expected_local_revision: u64) -> Result<CollectionMutationReport, CollectionError>`.

Migration report version1: ok, operation=migrate, outcome=migrated|idempotent, root_path NativePathReport, prior_schema_version, schema_version, prior_local_revision, local_revision, active_generation Option<String>. Existing mutation report version1 retains all fields; operations update/rebuild and outcomes updated/rebuilt/idempotent are explicit. Add typed `MigrationRequired { version }`, `RevisionConflict { expected, observed }` and `NotInstalled { pack: Option<PackId> }` (None for no active generation) variants/categories, preserving concrete cause/context and the complete existing CollectionFailureReport. No message parsing or new generic envelope.

CLI adds `collections migrate ROOT --expected-revision N`, `collections update ROOT <same manifest/sealed selectors as install> --expected-revision N`, `collections rebuild ROOT --expected-revision N`. All runtime selector/IO/serialization/output failures use the actual managed mutation envelope/outcome; Clap syntax stays Clap. Read-only list adds catalogue_schema_version so the prerequisite is discoverable. This is intentional additive evolution of the Serialize-only CollectionListReport version1 wire: every previous field/meaning remains, but whole-envelope bytes gain this field. Document and test that choice; do not claim exact old list-envelope bytes. Existing full query/envelope compatibility remains unchanged. Update/rebuild have no HOME/default lookup and use native ROOT/manifest/inputs with one frozen cwd, all-absolute no-cwd counterpart.

Update only replaces currently installed selected packs; unknown/uninstalled selected pack fails (install is the other operation). Unselected manifest inputs have no IO. Explicit expected revision protects stale callers and is checked before any stage allocation under the transaction. Normalize/strictly seal selected inputs, preserve full parsed seal equivalence (including kind/pins), replace only selected members, retain all others. A genuine different release may contain historically differing same-ID bodies, but the complete co-active set must pass existing exact identity composition. Retain old descriptors/releases and do not rewrite source history/ReleaseRecord.selected. A same complete seal/release update is idempotent after explicit current-store verification, retaining revision, content ID, generation ID and bytes. Different declaration over identical data is not an exact repeat.

Rebuild is FORCE new physical generation from exact current active owned release/seal copies; content ID/canonical bytes/model/provenance remain identical, generation ID/revision change. With no active members return typed NotInstalled/unavailable, not an empty successful build. Missing/tampered owned input fails even if old derived store is usable; this is explicit maintenance, not ordinary query. Rebuild can replace missing/corrupt derived indexes using intact sealed copies. Ordinary install remains additive and exact-repeat semantics are retained, but now reads only active membership/pointer and targets v2 physical tables.

Reuse strict load/consuming composition/DictionaryStore::create+All and checked digest equality, drop Store/model before subsequent heavy load, private0700/0600 and fsync before activation. Activation transaction commits generation+heads+pointer+revision+attempt together. Extend stage markers/orphan inspection for actual operation names without making abandoned stages active. Retain every old directory and external input byte. Precommit failure leaves prior state; explicit rollback/context; confirmed commit remains committed after receipt loss; uncertain commit/rollback is indeterminate. No fallback activation of a historical generation on corruption.
